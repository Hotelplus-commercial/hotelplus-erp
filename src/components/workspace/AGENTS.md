# Workspace rules

## Service tickets — receiver side (Receiver v1.0, ST46–ST60)
- §1 Switch: `service_sla: true` on the ORM · MARCOM · AC · BD rows of `WORKSPACES` (workspace-registry.ts). False elsewhere → 🎫 lane unchanged (PM · HR · AUTO · Office · AE My Day).
- §2 List: `ServiceReceiverLane` (service-receiver.tsx) reads `vServiceTickets()` only (L0 + PS cases via `ticketApi.list`, ticket_sla, ticket_followups). Words: New · กำลังดำเนินการ · รอลูกค้า · รอ 3rd Party · Solve · ยกเลิก. Pure helpers in src/lib/service-receiver.ts (laneRows / visibleRows / dueCell / followBadge / acceptChips / bellTarget). Members see the queue (New) + own; heads (GRM · Marcom Lead · AC Head (ทดสอบ) · BDM (ทดสอบ)) see all. FYI / watcher types stay in the old table below ("👁 แจ้งเพื่อทราบ"). BD keeps its old L0 table in full (L0 / L1 / R3.x acceptance), so BD service tickets also appear there.
- §3 Accept: modal → `acceptTicket()`; date chips +3/+5/+7/+10 from created date, picker limited to [today, created + 10]; heads may accept on behalf; write-once.
- §4 Panel: status actions → `changeTicketStatus()` (รอ 3rd Party needs รอใคร; อื่น ๆ needs text). PS cases: accept / due date / category / follow-ups only; status via "เปลี่ยนสถานะที่หน้าจอ case เดิม ↗" (/ps?tab=task). No Follow up button and no due-date edit on the receiver side.
- §5 Categories: gear "⚙️ หมวด ticket" for the head only; `checkCategoryOverlap` live → `addCategory` or locked → `requestCategory` (OGM). Head hides own-added only; system categories only OGM; no delete.
- §6 OGM: `OgmCategoryGroup` on the AUTO Workspace → `decideCategoryRequest` (reject needs a reason).
- §7 Shut-off / re-open (X4): the same SYSTEM_SHUTOFF / SYSTEM_REACTIVATE tickets (no copy); row/panel show type, contract, Partner system, AE and the twin PS ticket status (read only).
- "สมาชิกที่ดู (DEMO)" value is shared per Workspace via src/lib/ws-viewer.ts (Coaching picker on ORM / Marcom; lane picker on AC / BD). Simulation only, never security.
- Open items: Can PS cases be routed to BD? (file 1 routing currently ORM / MARCOM / AC). Receiver progress notes need a write path (file 1 has none) — note box hidden. Unhide category and OGM rename-before-approve have no file 1 service — hidden. Live mode has no named heads except BDM via the role switcher.

## Service tickets — SLA, categories, follow up (SLA Core v1.0, ST1–ST20)
- Scope: target ORM · MARCOM · AC · BD, both stores (Layer 0 + PS cases routed ORM/MARCOM/AC); FYI types GRADE_RISK · PARTNER_DEAL_NOTICE · SYSTEM_CREDIT_NOTICE and target PS are out. CANCELLED kept for history, never counted; median (never mean) for solve days.
- Labels: New · กำลังดำเนินการ (ACK + IN_PROGRESS) · รอลูกค้า · รอ 3rd Party · Solve · ยกเลิก; due states ยังไม่ใส่วันที่ · ทันกำหนด · เลยกำหนด. Internal codes never shown.
- Due date: set by the receiver in the same action as รับงาน, window [today, created + 10] calendar days (Asia/Bangkok), write-once (no edit / extension / reset on reopen); not set → effective due = created + 10 (AUTO). Clock never pauses. Overdue remark (HAD_WAIT / NOT_ACCEPTED) never changes counts. Old accepted tickets are never updated; the view gives them AUTO.
- Follow up: AE / PM only, open tickets, one per ticket per Bangkok day whoever sends; recipient = assignee, or dept queue + head when New.
- Categories: §5.1 system seed; only the department head adds for their own department (ORM GRM · MARCOM Marcom Lead · AC AC Head (ทดสอบ) · BD BDM (ทดสอบ)); deterministic overlap check (normalised contains / keyword / Levenshtein ≥ 0.6) refuses; conflict → request to OGM (ทดสอบ). Hide only, no delete path; system categories hidden only by OGM.
- Alerts (§7): TICKET_NEW · TICKET_NO_DATE_DAILY · TICKET_NOT_ACCEPTED_3D · TICKET_DUE_TOMORROW · TICKET_OVERDUE · TICKET_FOLLOWUP · CATEGORY_REQUEST into bell_items; every head alert also goes to the dept queue. No scheduler: computed on the first open of the day / on ticket changes, once-only keys.
- Storage: Layer 0 SLA fields are optional fields on the ticket record (accepted_by = assigned_to, label = assigned_to_label), written only via patchServiceTicket(); statuses WAITING_CUSTOMER / WAITING_THIRD_PARTY added to L0Status (count as open). PS cases live in the database but their SLA fields live in browser storage in the prototype (meridia.ticket_sla.v1 → ps:ticket_sla) — portal must add these as columns on the ticket table; never write the PS case tables or change ticket_create_v4 / ticket_update_v3. PS case waiting: CUSTOMER → รอลูกค้า, INTERNAL or any non-customer waiting_on → รอ 3rd Party; status changes for PS cases stay on the existing case screen.
- Collections (meridia.<name>.v1 → ps:<name>, DEMO in memory): ticket_categories · ticket_followups · ticket_category_requests · ticket_sla · bell_items. Rules/services only in src/lib/service-tickets.ts (vServiceTickets, acceptTicket, changeTicketStatus, sendFollowUp, changeTicketCategory, addCategory, hideCategory, checkCategoryOverlap, requestCategory, decideCategoryRequest); alerts src/lib/service-ticket-alerts.ts; bell glue src/lib/service-ticket-runtime.ts; DEMO src/lib/service-tickets-demo.ts.
- Bell items (src/lib/bell-items.ts): target USER / ROLE / DEPT_QUEUE, once-only key, read per viewer; the viewer comes from the Workspace role (queue + head role) or the DEMO member picker. Coaching and Welcome Back still use their Workspace groups and can move to bell_items later.
